Big Data Processing Questions 

Below are concise, interview-ready answers to the Big Data Processing questions. For senior-level interviews, expand the scenario answers with examples from  workforce analytics project.

# 1. Big Data Fundamentals

### 1. What is Big Data?

Big Data refers to datasets that are too large, fast, or complex to process efficiently using traditional databases. It commonly requires distributed storage and processing technologies such as Spark, Kafka, Hadoop, Databricks, and cloud data lakes.

### 2. What are the 5 Vs of Big Data?

The 5 Vs are:

* **Volume:** Large amounts of data.
* **Velocity:** The speed at which data is generated and processed.
* **Variety:** Structured, semi-structured, and unstructured data.
* **Veracity:** Data quality and reliability.
* **Value:** Useful business insights obtained from the data.

### 3. What is distributed computing?

Distributed computing divides a large processing workload across multiple machines. Each machine processes part of the data in parallel, which improves scalability and performance.

### 4. Why do we use distributed systems for Big Data?

A single machine has limited CPU, memory, and storage. Distributed systems allow us to process terabytes or petabytes of data by spreading the workload across multiple nodes while providing scalability and fault tolerance.

### 5. Horizontal scaling vs vertical scaling

Vertical scaling means increasing the CPU, memory, or storage of one machine. Horizontal scaling means adding more machines to a cluster. Big Data platforms normally use horizontal scaling because it is more flexible and cost-effective.

### 6. What is data partitioning?

Data partitioning divides a large dataset into smaller logical pieces based on a column such as date, region, or customer ID. It allows distributed processing engines to process partitions in parallel and skip unnecessary data.

### 7. What is data sharding?

Sharding distributes different subsets of data across separate database servers. Unlike basic partitioning inside one system, each shard may operate independently on a different machine.

### 8. What is fault tolerance?

Fault tolerance is the ability of a system to continue processing or recover when a node, task, or service fails. Spark achieves this through lineage and task retries, while HDFS uses data replication.

### 9. What is data locality?

Data locality means processing data close to where it is stored. This reduces network transfer and improves processing performance.

### 10. What is parallel processing?

Parallel processing means executing multiple tasks at the same time across different CPU cores or cluster nodes. Spark uses parallel tasks to process different data partitions simultaneously.

# 2. Apache Spark

### 11. What is Apache Spark?

Apache Spark is a distributed data processing engine used for batch processing, streaming, SQL, machine learning, and graph workloads. It processes data across multiple cluster nodes.

### 12. Why is Spark faster than Hadoop MapReduce?

Spark can keep intermediate data in memory, while MapReduce frequently writes intermediate results to disk. Spark also optimizes complete execution plans through its DAG scheduler.

### 13. Explain Spark architecture

A Spark application consists of:

* **Driver:** Coordinates the application.
* **Cluster manager:** Allocates resources.
* **Executors:** Process tasks and store intermediate data.
* **Worker nodes:** Machines where executors run.

### 14. Driver, executor, cluster manager, and worker

The driver creates the Spark session, builds the execution plan, and schedules tasks. Executors perform calculations. The cluster manager allocates resources. Worker nodes host executors.

### 15. What is an RDD?

RDD stands for Resilient Distributed Dataset. It is an immutable, distributed collection of objects that can be processed in parallel. It provides low-level control but fewer optimizations than DataFrames.

### 16. RDD vs DataFrame vs Dataset

* **RDD:** Low-level, flexible, but less optimized.
* **DataFrame:** Distributed table with named columns and Catalyst optimization.
* **Dataset:** Type-safe API available mainly in Scala and Java.

In PySpark, DataFrames are generally preferred.

### 17. What is lazy evaluation?

Spark does not execute transformations immediately. It records them and waits until an action such as `count()`, `show()`, or `write()` is called. This allows Spark to optimize the complete execution plan.

### 18. Transformations vs actions

Transformations create a new DataFrame or RDD, such as `filter()`, `select()`, and `join()`. Actions trigger actual execution, such as `count()`, `collect()`, and `write()`.

### 19. Narrow vs wide transformations

A narrow transformation does not require data movement between partitions, such as `filter()` or `map()`.

A wide transformation requires shuffle across partitions, such as `groupBy()`, `join()`, or `distinct()`.

### 20. What is a Spark DAG?

A DAG, or Directed Acyclic Graph, represents the sequence of transformations required to complete a Spark job. Spark divides the DAG into stages at shuffle boundaries.

### 21. Jobs, stages, and tasks

An action creates a job. A job is divided into stages based on shuffle boundaries. Each stage contains tasks, normally one task per partition.

### 22. What causes shuffle?

Operations such as joins, aggregations, `groupBy`, `distinct`, `repartition`, and sorting can cause shuffle because related records must be moved between executors.

### 23. Why is shuffle expensive?

Shuffle involves network transfer, disk I/O, sorting, serialization, and memory usage. It can become the main performance bottleneck in a Spark job.

### 24. What is Spark partitioning?

Spark divides data into partitions. Each partition is processed by one task. Proper partitioning helps distribute workloads evenly and enables parallel processing.

### 25. `repartition()` vs `coalesce()`

`repartition()` can increase or decrease partitions and performs a full shuffle. `coalesce()` is mainly used to reduce partitions and usually avoids a full shuffle.

### 26. What is a broadcast join?

A broadcast join sends a small table to every executor so that the large table does not need to be shuffled.

```python
from pyspark.sql.functions import broadcast

result = large_df.join(broadcast(small_df), "department_id")
```

### 27. When should you use a broadcast join?

Use it when one side of the join is small enough to fit safely into executor memory. Avoid broadcasting large tables because it may cause executor out-of-memory errors.

### 28. What is data skew?

Data skew occurs when some partitions contain much more data than others, often because one join or aggregation key appears very frequently. A few tasks then take much longer than the others.

### 29. How do you handle data skew?

I use:

* Adaptive Query Execution.
* Key salting.
* Broadcasting the smaller table.
* Filtering unnecessary data before joining.
* Splitting highly frequent keys.
* Increasing partitions when appropriate.

### 30. What is Adaptive Query Execution?

AQE allows Spark to change the execution plan during runtime. It can coalesce small partitions, optimize skewed joins, and change join strategies based on actual data statistics.

```python
spark.conf.set("spark.sql.adaptive.enabled", "true")
```

### 31. What is predicate pushdown?

Predicate pushdown sends filters closer to the storage layer so that only required rows are read. For example, a Parquet reader can skip row groups that do not match a filter.

### 32. What is partition pruning?

Partition pruning means reading only the storage partitions that match a query filter.

For example, filtering `event_date = '2026-07-12'` can avoid scanning all other date partitions.

### 33. What is caching?

Caching stores reused data in memory so Spark does not recompute it every time.

```python
df.cache()
df.count()
```

### 34. `cache()` vs `persist()`

`cache()` uses Spark’s default storage level. `persist()` allows you to select a specific storage level, such as memory only, memory and disk, or disk only.

### 35. When should you avoid caching?

Avoid caching when the DataFrame is used only once, is too large for available memory, or is inexpensive to recompute. Unnecessary caching can cause memory pressure and garbage collection.

### 36. What is checkpointing?

Checkpointing writes data and processing state to reliable storage and removes dependency on the original lineage. It is useful for long lineage chains and streaming recovery.

### 37. Caching vs checkpointing

Caching improves performance but preserves lineage and may be lost. Checkpointing provides fault recovery by writing data to reliable storage and truncating lineage.

### 38. How do you optimize a slow Spark job?

I examine the Spark UI, execution plan, stage durations, shuffle size, skew, spills, partition count, and join strategies. I then apply filtering, partition pruning, broadcasting, AQE, improved partitioning, and better file sizing.

### 39. How do you identify executor memory issues?

I check the Spark UI and executor logs for:

* Out-of-memory exceptions.
* High garbage collection time.
* Excessive disk spill.
* Executor loss.
* Large broadcast variables.
* Large or skewed partitions.

### 40. What causes out-of-memory errors?

Common causes include:

* Large partitions.
* Collecting excessive data to the driver.
* Broadcasting a large table.
* Heavy caching.
* Data skew.
* Insufficient executor memory overhead.
* Too many records processed in one task.

# 3. Spark Performance Optimization

### 41. How do you determine the number of partitions?

I consider data volume, cluster cores, target file size, shuffle volume, and task duration. A common starting point is two to four times the total executor cores, followed by tuning through Spark UI metrics.

### 42. What is the small-file problem?

A large number of small files increases metadata operations, task scheduling overhead, and storage API calls. It can make Spark spend more time opening files than processing data.

### 43. How do you handle millions of small files?

I compact files periodically, control the number of output partitions, use optimized writes, use `OPTIMIZE` for Delta tables, and prevent excessively frequent small micro-batch writes.

### 44. How does file size affect performance?

Very small files create excessive overhead, while very large files reduce parallelism. For analytical workloads, files are often targeted around 128 MB to 1 GB depending on the platform and workload.

### 45. Sort-merge join vs broadcast hash join

A sort-merge join shuffles and sorts both large datasets by the join key. A broadcast hash join sends a small table to all executors and avoids shuffling the large dataset.

### 46. What is salting?

Salting adds an additional value to a skewed join key to distribute records across multiple partitions.

### 47. How does salting solve skew?

The frequent key is divided into several salted versions, such as `customer_1_0`, `customer_1_1`, and `customer_1_2`. This prevents all records for that key from going to one partition.

### 48. What is dynamic partition pruning?

Dynamic partition pruning uses values from one side of a join to eliminate unnecessary partitions from the other side at runtime.

### 49. How do you reduce shuffle?

I:

* Filter early.
* Select only required columns.
* Broadcast small tables.
* Avoid unnecessary `repartition()` and `distinct()`.
* Pre-aggregate data.
* Reuse appropriately partitioned datasets.
* Enable AQE.

### 50. How do you join two very large datasets?

I filter both datasets first, choose a well-distributed join key, ensure sufficient shuffle partitions, use partition pruning, handle skewed keys, and allow Spark to use sort-merge join. I also consider bucketing or incremental processing.

### 51. How do you tune executor memory?

I size executor memory based on partition size, caching, shuffle requirements, and cluster resources. I avoid extremely large executors because they can increase garbage collection pauses.

### 52. Executor memory overhead vs driver memory

Executor memory is used for task execution, caching, and shuffle operations. Memory overhead supports off-heap memory, Python processes, containers, and native libraries. Driver memory stores application metadata and collected results.

### 53. What is garbage collection?

Garbage collection removes unused objects from JVM memory. Excessive garbage collection reduces task performance and can indicate poor partition sizing or memory pressure.

### 54. What is disk spill?

Disk spill occurs when Spark cannot keep intermediate shuffle or aggregation data in memory and writes it to disk. Some spill is normal, but excessive spill indicates memory or partitioning problems.

### 55. How do you analyze a Spark execution plan?

I use `explain()` to review logical and physical plans. I check scans, filters, join strategies, exchanges, partition pruning, and whether unnecessary shuffles are present.

```python
df.explain("formatted")
```

### 56. What are Spark `explain()` modes?

Common modes are:

* `simple`
* `extended`
* `formatted`
* `cost`
* `codegen`

The formatted plan is particularly useful for reviewing physical operators.

### 57. What is Catalyst Optimizer?

Catalyst is Spark SQL’s query optimizer. It applies rules such as predicate pushdown, column pruning, constant folding, and join optimization.

### 58. What is Tungsten?

Tungsten is Spark’s execution engine improvement that optimizes memory management, CPU usage, binary processing, and code generation.

### 59. What is whole-stage code generation?

Whole-stage code generation combines multiple physical operators into optimized Java bytecode, reducing function-call overhead and improving CPU efficiency.

### 60. How does serialization affect performance?

Serialization converts objects into bytes for network transfer or storage. Efficient serializers reduce memory usage and network overhead. Spark commonly uses Kryo when optimized object serialization is required.

# 4. Batch Processing

### 61. What is batch processing?

Batch processing collects data over a period and processes it together at a scheduled time, such as hourly, daily, or weekly.

### 62. Give a batch-processing example

A daily workforce analytics pipeline reads employee activity files from S3, transforms them in Databricks, and loads curated data into Snowflake for reporting.

### 63. Advantages and disadvantages of batch processing

Batch processing is efficient for large volumes, easier to manage, and cost-effective. Its main disadvantage is higher latency compared with real-time streaming.

### 64. How do you design a scalable batch pipeline?

I use distributed processing, partitioned cloud storage, incremental ingestion, idempotent transformations, workflow orchestration, data quality validation, monitoring, retries, and separate Bronze, Silver, and Gold layers.

### 65. How do you process several terabytes daily?

I partition the input, process it incrementally using Spark, filter early, use columnar formats, optimize joins, distribute work across autoscaling clusters, and write appropriately sized output files.

### 66. How do you make a batch pipeline incremental?

I process only records newer than the last successful watermark, version, timestamp, or CDC offset. I then use merge or upsert logic instead of reloading the entire dataset.

### 67. What is CDC?

Change Data Capture identifies inserts, updates, and deletes in a source system and sends only those changes to downstream systems.

### 68. How do you process newly arrived records?

I track a watermark, ingestion timestamp, source sequence number, or file metadata. The next run reads only data newer than the stored checkpoint.

### 69. How do you handle late-arriving batch data?

I use event dates rather than ingestion dates, reopen affected partitions, use merge operations, and rerun only the impacted processing window.

### 70. How do you rerun a failed batch safely?

I make the pipeline idempotent. I use deterministic keys, transactional writes, staging tables, merge operations, checkpoints, and cleanup of incomplete outputs.

# 5. Streaming Processing

### 71. What is stream processing?

Stream processing continuously processes events as they arrive, rather than waiting for a scheduled batch.

### 72. Batch vs stream processing

Batch processing handles accumulated datasets at scheduled intervals. Streaming processes events continuously with lower latency.

### 73. What is micro-batch processing?

Micro-batch processing groups events into very small batches, such as every few seconds, and processes each batch incrementally. Spark Structured Streaming commonly uses this model.

### 74. What is Spark Structured Streaming?

Spark Structured Streaming is a stream-processing engine built on Spark SQL. Developers define streaming transformations using DataFrame APIs.

### 75. How does Structured Streaming work?

Spark continuously reads new data from a source, applies DataFrame transformations, and writes results to a sink. It stores progress and state in checkpoint storage.

### 76. What is a streaming checkpoint?

A checkpoint stores source offsets, state, and processing progress. It enables a streaming query to restart from the correct location after failure.

### 77. What is a watermark?

A watermark defines how long the system should wait for late-arriving events before old state can be removed.

### 78. Why are watermarks used?

Watermarks prevent state from growing indefinitely in stateful operations such as aggregations, deduplication, and stream-stream joins.

### 79. What is late-arriving data?

Late-arriving data is an event that reaches the processing system later than its actual event time, often because of network, device, or upstream delays.

### 80. How do you handle duplicate streaming events?

I use a unique event ID, watermarking, and deduplication.

```python
clean_df = (
    stream_df
    .withWatermark("event_time", "15 minutes")
    .dropDuplicates(["event_id"])
)
```

### 81. What is stateful stream processing?

Stateful processing keeps information across events or micro-batches, such as running counts, sessions, windows, and deduplication keys.

### 82. What is stateless processing?

Stateless processing handles each event independently without maintaining information about previous events. Examples include filtering and column transformations.

### 83. What is event time?

Event time is when the business event actually occurred at the source.

### 84. What is processing time?

Processing time is when the processing engine handles the event.

### 85. What is ingestion time?

Ingestion time is when the event enters the messaging or data-processing platform.

### 86. What is exactly-once processing?

Exactly-once means each event affects the final result only once, even if retries or failures occur. It normally requires replayable sources, checkpoints, idempotent sinks, and transactional writes.

### 87. What is at-least-once processing?

At-least-once guarantees that an event is processed one or more times. It avoids data loss but may produce duplicates.

### 88. What is at-most-once processing?

At-most-once means an event is processed zero or one time. It avoids duplicates but may lose events during failure.

### 89. How do you recover a failed streaming pipeline?

I restart it using the same checkpoint location. The engine restores offsets and state and continues from the last successfully committed batch.

### 90. How do you monitor streaming latency?

I monitor input rate, processed rate, batch duration, event-time delay, Kafka consumer lag, state-store size, failed batches, and end-to-end SLA.

# 6. Apache Kafka

### 91. What is Apache Kafka?

Kafka is a distributed event-streaming platform used for publishing, storing, and consuming high-volume event data.

### 92. What are Kafka brokers?

Brokers are Kafka servers that store topic partitions and serve producer and consumer requests.

### 93. What is a Kafka topic?

A topic is a logical stream or category of messages, such as `employee_activity` or `payment_events`.

### 94. What are Kafka partitions?

A topic is divided into partitions. Each partition is an ordered, append-only log that can be processed independently.

### 95. Why are partitions important?

Partitions provide scalability and parallelism. Multiple consumers can process different partitions simultaneously.

### 96. What is a Kafka producer?

A producer publishes messages to a Kafka topic. It may choose a partition using a message key or partitioning strategy.

### 97. What is a Kafka consumer?

A consumer reads messages from one or more topic partitions and tracks its progress using offsets.

### 98. What is a consumer group?

A consumer group is a collection of consumers working together. Each partition is assigned to only one consumer within the group at a time.

### 99. How are partitions assigned to consumers?

Kafka’s group coordinator assigns partitions using a partition assignment strategy. When consumers join or leave, Kafka may rebalance the assignments.

### 100. What is an offset?

An offset is the sequential position of a message within a Kafka partition. Consumers use offsets to track which messages they have processed.

### 101. What is Kafka rebalancing?

Rebalancing redistributes topic partitions among consumers in a consumer group.

### 102. What causes rebalancing?

Common causes include:

* A consumer joining or leaving.
* Consumer failure.
* Session timeout.
* Partition-count changes.
* Subscription changes.

### 103. What is message retention?

Retention determines how long Kafka keeps messages or how much log storage is allowed, regardless of whether consumers have read them.

### 104. What is log compaction?

Log compaction retains the latest message for each key. It is useful for rebuilding the latest state of entities.

### 105. Retention vs log compaction

Time- or size-based retention removes old records. Log compaction keeps the latest value for each key, even if older values are removed.

### 106. How does Kafka maintain ordering?

Kafka guarantees message ordering within an individual partition. Messages with the same key should be sent to the same partition.

### 107. Does Kafka guarantee global ordering?

No. Kafka guarantees ordering only within a partition, not across all partitions in a topic.

### 108. How do you handle duplicate Kafka messages?

I use idempotent producers, transactional publishing where appropriate, unique event identifiers, consumer-side deduplication, and idempotent database writes.

### 109. What happens when a broker fails?

The partition leader on the failed broker becomes unavailable temporarily. Kafka elects an in-sync replica on another broker as the new leader.

### 110. What is replication factor?

Replication factor is the number of copies of each partition stored across Kafka brokers. A replication factor of three means one leader and two replicas.

### 111. Leader vs follower partitions

The leader handles reads and writes. Followers replicate the leader’s data and may become leader if the current leader fails.

### 112. How do you improve Kafka throughput?

I increase partitions, batch producer messages, enable compression, tune acknowledgment settings, optimize message size, scale consumers, and ensure sufficient broker resources.

### 113. What is Kafka consumer lag?

Consumer lag is the difference between the latest offset available in a partition and the last offset processed by the consumer.

### 114. How do you monitor Kafka lag?

I monitor lag by topic, partition, and consumer group using tools such as Kafka metrics, Prometheus, Grafana, Datadog, or managed Kafka monitoring.

### 115. How would you process one million events daily?

I would partition the Kafka topic using an appropriate business key, use Spark Structured Streaming consumers, store checkpoints in reliable storage, deduplicate using event IDs, and write idempotently to Delta Lake or another transactional sink.

# 7. Hadoop and HDFS

### 116. What is Hadoop?

Hadoop is an ecosystem for distributed storage and processing of large datasets. Its core components include HDFS, YARN, and MapReduce.

### 117. Main Hadoop components

* **HDFS:** Distributed storage.
* **YARN:** Resource management.
* **MapReduce:** Batch-processing framework.
* **Hadoop Common:** Shared libraries and utilities.

### 118. What is HDFS?

HDFS is a distributed file system that stores large files across multiple cluster nodes using blocks and replication.

### 119. What is a NameNode?

The NameNode manages HDFS metadata, including filenames, directories, permissions, and the locations of file blocks.

### 120. What is a DataNode?

A DataNode stores actual HDFS data blocks and reports its status to the NameNode.

### 121. What is the HDFS replication factor?

It is the number of copies maintained for each block. The traditional default is three, although it can be configured.

### 122. Why does HDFS use replication?

Replication protects data against machine or disk failure and allows data to remain available when a DataNode fails.

### 123. What happens when a DataNode fails?

The NameNode detects missed heartbeats, marks the node unavailable, and arranges replication of under-replicated blocks from existing copies.

### 124. What happens when the NameNode fails?

In a high-availability configuration, a standby NameNode takes over. Without high availability, the cluster may become temporarily inaccessible.

### 125. What is Hadoop MapReduce?

MapReduce is a batch-processing model where map tasks transform input records and reduce tasks aggregate records grouped by key.

### 126. MapReduce vs Spark

MapReduce writes intermediate results to disk and is mainly designed for batch processing. Spark supports in-memory processing, SQL, streaming, and more advanced optimizations.

### 127. What is YARN?

YARN manages cluster resources and schedules applications across Hadoop nodes.

### 128. What is the ResourceManager?

The ResourceManager controls cluster-wide resource allocation and coordinates application scheduling.

### 129. What is the NodeManager?

A NodeManager runs on each worker node and manages containers, resource usage, and task execution on that node.

### 130. What is the small-file problem in HDFS?

Every file and block requires NameNode metadata. Millions of small files can consume excessive NameNode memory and create processing overhead.

# 8. Data Lake and Lakehouse

### 131. What is a data lake?

A data lake stores large volumes of raw and processed data in scalable object storage, including structured, semi-structured, and unstructured data.

### 132. What is a data warehouse?

A data warehouse stores cleaned, structured, and modeled data optimized for SQL analytics and business reporting.

### 133. What is a data lakehouse?

A lakehouse combines scalable, low-cost data-lake storage with warehouse features such as ACID transactions, governance, schema enforcement, and SQL performance.

### 134. Data lake vs lakehouse

A traditional data lake mainly provides storage and may have limited transactional control. A lakehouse adds table management, reliability, governance, and query optimization.

### 135. What is Medallion Architecture?

Medallion Architecture organizes data into progressive quality layers: Bronze, Silver, and Gold.

### 136. Bronze, Silver, and Gold

* **Bronze:** Raw ingested data.
* **Silver:** Validated, cleaned, standardized, and deduplicated data.
* **Gold:** Aggregated and business-ready datasets.

### 137. What is Delta Lake?

Delta Lake is an open table format that adds ACID transactions, schema management, time travel, merge operations, and reliability to data stored in object storage.

### 138. What are ACID transactions?

ACID stands for atomicity, consistency, isolation, and durability. These properties ensure data operations remain reliable even during concurrent writes or failures.

### 139. Why are ACID transactions important in a data lake?

They prevent readers from seeing partial writes, support safe concurrent operations, and make updates, deletes, and merges reliable.

### 140. What is schema enforcement?

Schema enforcement rejects records or writes that do not match the expected table schema.

### 141. What is schema evolution?

Schema evolution allows controlled changes such as adding new columns without rebuilding the entire table.

### 142. What is Delta Lake time travel?

Time travel allows users to query an older table version or timestamp for auditing, recovery, and comparison.

```sql
SELECT *
FROM employees VERSION AS OF 12;
```

### 143. What is the Delta transaction log?

The transaction log records table versions, file additions, file removals, schema changes, and transaction metadata.

### 144. What is `_delta_log`?

`_delta_log` is the directory containing JSON transaction records and checkpoint files for a Delta table.

### 145. What is `OPTIMIZE`?

`OPTIMIZE` compacts many small Delta files into fewer, larger files to improve query performance.

### 146. What is Z-Ordering?

Z-Ordering colocates related values within files, allowing Delta queries to skip more irrelevant data for frequently filtered columns.

### 147. Partitioning vs Z-Ordering

Partitioning creates separate directory-level partitions. Z-Ordering organizes values inside data files. Partitioning is better for low-cardinality columns; Z-Ordering can help with moderately high-cardinality filter columns.

### 148. What is `VACUUM`?

`VACUUM` removes data files that are no longer referenced by the current Delta table and are older than the configured retention period.

### 149. What are deletion vectors?

Deletion vectors mark rows as logically deleted without immediately rewriting complete Parquet files. This can improve delete and merge performance.

### 150. How do you handle schema changes?

I validate schema changes, maintain schema contracts, allow safe additions through controlled evolution, quarantine incompatible records, and version transformations when breaking changes occur.

# 9. Data Formats

### 151. CSV vs JSON vs Parquet vs Avro

* **CSV:** Simple text, no rich schema, inefficient for large analytics.
* **JSON:** Flexible and readable, but verbose.
* **Parquet:** Columnar and highly efficient for analytics.
* **Avro:** Row-oriented, schema-based, and suitable for event transport.

### 152. Why is Parquet preferred?

Parquet provides column pruning, predicate pushdown, compression, and efficient analytical scans.

### 153. What is a columnar format?

A columnar format stores values from the same column together. Queries can read only required columns rather than complete rows.

### 154. Predicate pushdown in Parquet

Spark uses Parquet statistics to avoid reading row groups that cannot satisfy the query filter.

### 155. What is column pruning?

Column pruning means reading only the columns needed by the query, reducing data transfer and memory usage.

### 156. What is compression?

Compression reduces file size by encoding data more efficiently. It lowers storage and network costs, although decompression consumes some CPU.

### 157. Snappy vs Gzip

Snappy provides fast compression and decompression with a moderate compression ratio. Gzip creates smaller files but uses more CPU and is generally slower.

### 158. Why is Avro used with Kafka?

Avro provides compact row-based serialization and strong schema support. It works well with schema registries and evolving event schemas.

### 159. When would you use JSON instead of Parquet?

I use JSON for APIs, message payloads, logs, and flexible semi-structured data exchange. I use Parquet for analytical storage and large-scale processing.

### 160. What is ORC?

ORC is a columnar storage format optimized for analytical workloads, particularly in Hadoop and Hive ecosystems.

# 10. Cloud Big Data

### 161. What is AWS EMR?

Amazon EMR is a managed service for running distributed frameworks such as Spark, Hadoop, Hive, and Trino on AWS.

### 162. How does EMR process Big Data?

EMR provisions a cluster, reads data from sources such as S3, distributes processing across nodes, and writes results back to storage or analytical systems.

### 163. EMR vs AWS Glue

EMR provides greater control over clusters, frameworks, and tuning. Glue is more serverless and managed, making it convenient for ETL jobs that require less infrastructure control.

### 164. EMR vs Databricks

EMR is an AWS-managed platform supporting multiple open-source frameworks. Databricks provides a more integrated lakehouse platform with collaborative notebooks, optimized Spark, governance, Delta Lake, and managed workflows.

### 165. What is AWS Kinesis?

Kinesis is an AWS service family for collecting, processing, and delivering real-time streaming data.

### 166. Kafka vs Kinesis

Kafka offers greater portability, ecosystem flexibility, and operational control. Kinesis is tightly integrated with AWS and provides managed scaling and security.

### 167. What is Azure Databricks?

Azure Databricks is a managed lakehouse and analytics platform built around Apache Spark and integrated with Azure services.

### 168. What is Azure Synapse Analytics?

Azure Synapse is an analytics service combining data integration, data warehousing, serverless SQL, Spark, and reporting integrations.

### 169. What is Azure Event Hubs?

Azure Event Hubs is a managed event-ingestion service designed for high-volume streaming data.

### 170. Event Hubs vs Kafka

Event Hubs is a fully managed Azure service and supports Kafka-compatible endpoints. Kafka provides a broader open-source ecosystem and more deployment control.

### 171. How do you process data stored in S3?

I read partitioned Parquet or Delta data using Spark on Databricks, EMR, or Glue. I apply filtering and transformations and write curated results back to optimized storage or a warehouse.

### 172. How do you process ADLS data?

I use secure managed identities or service principals, mount or directly access ADLS, process files using Databricks or Synapse Spark, and store curated Delta tables.

### 173. How do you optimize cloud storage cost?

I use lifecycle policies, compression, columnar formats, appropriate storage tiers, retention rules, incremental processing, and cleanup of obsolete files.

### 174. How do you design a multi-cloud platform?

I use open formats such as Parquet, Delta, or Iceberg; infrastructure as code; loosely coupled services; centralized governance; portable Spark and dbt transformations; and cloud-specific adapters.

### 175. What is autoscaling?

Autoscaling automatically increases or decreases cluster resources based on workload demand. It improves resource utilization and reduces cost.

# 11. Data Quality and Reliability

### 176. How do you maintain data quality?

I implement schema validation, null checks, uniqueness checks, referential-integrity checks, freshness checks, reconciliation, range checks, anomaly detection, and quarantine handling.

### 177. What validation checks do you perform?

Typical checks include:

* Record count.
* Duplicate detection.
* Null percentage.
* Data type validation.
* Range validation.
* Referential integrity.
* Freshness.
* Source-to-target reconciliation.

### 178. How do you identify duplicates?

I use business keys, event IDs, row hashes, or window functions.

```sql
SELECT *
FROM (
    SELECT *,
           ROW_NUMBER() OVER (
               PARTITION BY employee_id, event_time
               ORDER BY ingestion_time DESC
           ) AS rn
    FROM employee_events
) t
WHERE rn > 1;
```

### 179. How do you handle null values?

I first determine whether the null is valid. Depending on the business rule, I reject the record, replace the null with a default, derive the value, or allow it while generating a quality warning.

### 180. How do you handle malformed records?

I store malformed records in a quarantine or dead-letter location with error details. The valid records continue processing while rejected records are reviewed separately.

### 181. What is schema drift?

Schema drift occurs when the source schema changes unexpectedly, such as new columns, removed fields, or changed data types.

### 182. How do you handle upstream schema changes?

I use schema contracts, validation at ingestion, alerts, controlled schema evolution, backward-compatible transformations, and quarantine for incompatible records.

### 183. What is data reconciliation?

Data reconciliation compares source and target data to confirm that records, totals, and important business values were transferred correctly.

### 184. How do you validate source and target counts?

I compare total counts, counts by partition or date, distinct business keys, sum totals, rejected-record counts, and control-table metrics.

### 185. What is idempotency?

Idempotency means rerunning the same operation with the same input produces the same final result without duplicate or inconsistent data.

### 186. Why should pipelines be idempotent?

Failures and retries are normal in production. Idempotency allows safe reruns without creating duplicate data or corrupting the target.

### 187. How do you avoid duplicates during reruns?

I use merge operations based on unique business keys, overwrite only affected partitions, track processed files, and write through staging tables before committing.

### 188. How do you build fault-tolerant pipelines?

I use checkpoints, retries, transactional storage, idempotent logic, durable message queues, monitoring, alerting, dead-letter queues, and restartable processing steps.

### 189. How do you implement retries?

I configure retries with exponential backoff for temporary failures. I limit the retry count and send permanently failed items to a dead-letter queue or quarantine location.

### 190. What is a dead-letter queue?

A dead-letter queue stores messages that could not be processed successfully after repeated attempts. It prevents bad events from blocking the main pipeline.

# 12. Scenario-Based Interview Answers

### 191. A Spark job increased from 30 minutes to three hours. How would you investigate?

I would first check whether input volume, file count, schema, or upstream distribution changed. In Spark UI, I would review stage durations, shuffle read and write, disk spill, garbage collection, skewed tasks, executor failures, and join strategies.

I would also compare the current execution plan with the previous plan. Likely fixes could include partition pruning, compacting small files, broadcasting a lookup table, handling skewed keys, increasing shuffle partitions, enabling AQE, or adjusting cluster resources.

### 192. One join key contains 70% of all records. What would you do?

This is severe data skew. I would isolate the heavy key and process it separately or apply salting to distribute it across multiple partitions. If the other table is small, I would use a broadcast join.

I would also enable AQE skew-join handling and verify that the key is not caused by invalid values such as `NULL` or `UNKNOWN`.

### 193. You receive five terabytes daily. How would you design the pipeline?

I would ingest data incrementally into a partitioned Bronze layer in cloud object storage. Spark on Databricks or EMR would clean and standardize it into a Silver Delta layer. Business aggregates would be written to the Gold layer or Snowflake.

I would use Parquet or Delta, partition pruning, CDC, autoscaling clusters, Airflow orchestration, data quality checks, idempotent writes, monitoring, and lifecycle policies.

### 194. Your job produces thousands of small files. How would you fix it?

I would reduce output partitions before writing, use optimized writes or auto-compaction, and schedule Delta `OPTIMIZE` operations. For streaming, I would increase the trigger interval to avoid creating very small micro-batches.

I would avoid forcing a single output file because that creates a scalability bottleneck.

### 195. A streaming pipeline creates duplicates. What would you do?

I would check whether the source provides at-least-once delivery and whether offsets are being committed correctly. I would ensure the pipeline uses a stable checkpoint location.

I would deduplicate using a unique event ID and watermark and make the destination write idempotent through merge or transactional operations.

### 196. A Kafka consumer is falling behind. How would you troubleshoot it?

I would compare the producer input rate with the consumer processing rate. Then I would inspect partition-level lag, consumer errors, processing latency, CPU, memory, network, downstream write speed, and rebalancing frequency.

Potential fixes include increasing consumers up to the partition count, increasing partitions, optimizing processing logic, increasing batch size, and improving downstream throughput.

### 197. Spark executors repeatedly run out of memory. What would you check?

I would check partition sizes, skew, caching, broadcast sizes, joins, collection operations, and Python UDF usage. Spark UI would show executor loss, garbage collection time, spill, and skewed tasks.

I would divide large partitions, fix skew, remove unnecessary caching, avoid `collect()`, tune executor memory overhead, and revise the join strategy.

### 198. A large table joins with a small lookup table. Which strategy would you use?

I would use a broadcast hash join because the small table can be copied to each executor. This avoids shuffling the large dataset.

I would first confirm that the lookup table safely fits into executor memory.

### 199. Data arrives after the daily pipeline finishes. What would you do?

I would use the event date as the business partition and maintain a configurable late-arrival window. The pipeline would reprocess only affected partitions and merge newly arrived records using a business key.

I would also track completeness and update downstream aggregates when late data changes previous results.

### 200. The source unexpectedly adds new columns. How would you handle it?

The ingestion layer would preserve the new fields where possible, but schema validation would detect the change and generate an alert. Safe additions could be accepted through controlled schema evolution.

Breaking changes, such as incompatible data types, would be quarantined until the transformation and target schemas were updated.

## How do you choose a partition column?

I choose a column that is frequently used in query filters and has balanced data distribution. Date is commonly suitable for time-based pipelines.

I avoid very high-cardinality columns such as unique user IDs and very low-cardinality columns that create only a few large partitions.

## How do you handle executor out-of-memory errors?

I first determine whether the issue comes from data skew, oversized partitions, broadcasting, caching, large aggregations, or collecting data to the driver.

I fix the processing pattern before simply increasing memory. I may repartition the data, salt skewed keys, remove unnecessary caching, reduce data early, increase memory overhead, or change the join strategy.

## How do you guarantee idempotency?

I use deterministic business keys, processed-file tracking, transactional tables, staging areas, and merge-based writes. For streaming, I combine checkpoints with unique event IDs and idempotent target operations.

This ensures that retrying a failed batch does not create duplicates.
