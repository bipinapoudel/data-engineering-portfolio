Pipeline Fails
Priority is to access the impact and restore the pipeline as quickly and safely as possible. I would not panic or make random changes instead I 
will follow the incident process step by step. 
First I will check the alert details in the monitoring tools like cloudwatch, Airflow, Grafana or pipeline logs to detect which job get
failed, when it failed and what the error message says. 
secondly I would identify the type of error. Fort e.g. it could be a source file missing, memory issue, permission issue, 
data quality failure, API timeout, etc.
Third, I would check whether the failure is impacting business reporting SLA dashboards or downstream teams. If the situation is critical, 
I will notify the responsible stakeholders or on-call team with a clear update.
Fourth I would try safe recovery steps, such as rerunning the failed task, restarting the job from the failed step, checking job bookmarks,
validating input data or increasing resources if it is a memory issue.
If the issue is related to bad records or schema mismatch, I will isolate the bad records or move them in a quarantine path if available, then start processing records.
Finally when the pipeline gets restored, I would document the root cause, what actions was taken and how to prevent it in the future.
My goal is to restore service quickly protect data accuracy and make sure the same issue doesn't happen again.

SQuirrel 
Currently, at Skill Squirrel, I am working on a Workforce Analytics Lakehouse project where the goal is to build scalable batch and streaming data pipelines for candidate, job, recruiter, and application activity data.

The project uses Azure Data Factory for ingestion and orchestration, Azure Data Lake Storage Gen2 for data storage, Azure Databricks and PySpark for transformation, Delta Lake for reliable data management, Kafka and Spark Structured Streaming for real-time candidate activity events, and Snowflake or Power BI for reporting and analytics.

The pipeline follows Medallion Architecture. In the Bronze layer, we store raw data from different sources. In the Silver layer, we clean the data, remove duplicates, handle null values, standardize formats, and validate the data. In the Gold layer, we create business-ready tables for workforce analytics, such as candidate activity trends, recruiter performance, job application status, time-to-hire, and hiring funnel metrics.

One major challenge I faced was duplicate and inconsistent candidate data coming from multiple systems. For example, the same candidate could appear with different email formats, missing fields, or different application statuses. I handled this using PySpark cleaning logic, standardization, and window functions to keep the latest valid candidate record.

Another challenge was slow Spark job performance while joining large candidate, job, and application datasets. I improved the performance by using proper partitioning, broadcast joins for smaller lookup tables, caching only when needed, and adaptive query execution.

I also worked on data quality checks to identify null values, duplicate records, invalid dates, and incorrect status values before moving the data to the Gold layer. This helped improve the reliability of reporting and reduced manual validation work.

This project helped me strengthen my hands-on skills in Azure Databricks, PySpark, Delta Lake, Kafka streaming, Medallion Architecture, Spark optimization, and building production-ready data pipelines for analytics.
